# Per-worker inode cap — 17 October 2026

The user selected **4,096** after initially considering 128. The 128 cap and experimental 16,384 cap were never deployed. All six graders now use `/var/local/lib/isolate:rw,exec,nosuid,size=256m,nr_inodes=4096` for their private tmpfs.

This limits allocated filesystem objects across each worker's sandbox, compiled baseline, private temporary directories and Isolate control area. Read-only testcases, normal RAM allocations, standard libraries, checker workspaces and logging outside the tmpfs do not consume this inode quota. Inodes are distinct filesystem objects: hard-link names can share an inode, so this is not an absolute cap on every possible directory entry/name. The existing data-size limit, CPU/wall limits, operation watchdogs and restart fallback remain in effect.

## Measured ordinary usage

The separate [usage measurement](SANDBOX-FILE-USAGE-20261017.md) found 6 regular files + 9 directories for ordinary C/C++ (15 total), 6 + 11 for Python (17), and 9 + 11 for Python importing one problem library (20). Five accepted C++ references across 198 testcases also peaked at 15. Snapshots counted visible objects exactly; inode peaks were sampled every 2 ms and may miss shorter-lived temporary peaks. Those measurements characterize tested programs, not every possible problem library.

## Validation

- A maximum-speed nested-directory program reached depth **4,081** under both one- and five-second CPU limits, then hit `No space left on device`. It deliberately spun after allocation failure and received normal TLE verdicts. Whole diagnostic job times were **1.657 s** and **5.686 s**; a subsequent healthy job received AC in **0.451 s**, in the same grader process. These include compilation/cleanup/observation and are not cleanup-only benchmarks.
- Five quota-policy scenarios passed: C++ and Python allocation exhaustion produced ordinary runtime-error verdicts, later C++/Python jobs passed, and scratch files reset between testcases.
- Fourteen ordinary verdict/custom-checker tests, 24 expanded C/C++/Python/subtask/Codeforces checks, 17 filesystem-isolation checks, and five accepted reference suites passed under the cap.
- Existing file I/O remained supported. No production submission was fabricated, rejudged or cancelled by the validation.

## Deployment

Only the tmpfs inode mount option changed. Source/native binary mounts and image identity remain the directory-depth release; CPU affinity, RAM/swap/PID limits, data-size cap, time limits, scoring, per-user/problem admission policies and restart behavior remain unchanged.

The first attempt automatically rolled back because live API rejudge requests deleted/requeued results while the strict before/after fingerprint comparison ran. Sanitized access-log timestamps confirmed concurrent rejudge activity. No database restore was performed. A retry paused new claims, allowed all active jobs to finish, waited for stable result fingerprints and replaced only the six graders. Existing results/policies matched after replacement, all six mounts reported exactly 4,096 inodes, and previous enabled states were restored with timestamp guards. Website/control services were not restarted. Subsequent live rejudges resumed normally.

All six graders and localhost/ngrok were checked after deployment. The maintenance compose copy on D was synchronized.
